# FTPS certificate and identity verification

The lint review traced Commons Net3.13.0’s permissive certificate helpers to the actual FileCore Session FTPS constructor. Its old default checks certificate dates without establishing a CA chain, and hostname checking defaults off. This is separate from the reviewed native FFmpeg/OpenSSL and Java HTTPS paths.

`FtpsTlsPolicy` now installs the platform default X509 trust manager. Failure to initialize trust fails closed. The control channel uses an explicit strict hostname verifier obtained from OkHttp’s public client configuration API. The data channel verifies the original control hostname after its TLS handshake and before returning any stream to application code. It never trusts a PASV/reverse-DNS identity instead. PROT P remains mandatory in Session; failed control/data sockets close. No process-global verifier/trust manager changes.

Five shared tests execute real local explicit FTPS/TLS connections: permissive upstream defaults accept an untrusted/wrong-host peer (negative control), trusted control/data transfer succeeds, the platform rejects the private fixture CA, a trusted CA with the wrong control hostname fails, and a trusted CA with the wrong data hostname fails. The fixture keys are generated public test-only material embedded in test source, never production signing credentials. All five pass in three repeated host trials using the same OkHttp5.5.1 JVM variant. Expected broken pipes are accepted only for rejected-peer fixtures; unexpected trusted-transfer server failures still fail. The complete FileCore suite uses the Android variant under Robolectric.

Actual Android23 execution reproduced `NoSuchMethodError` for SSLParameters.setEndpointIdentificationAlgorithm, so the unsupported optional setter was removed. Commons Net’s explicit verifier still checks control identity, and the same strict verifier checks data identity; no hostname/chain bypass is substituted. Actual-framework run40884866451 passes all28 cases (22Jetty,1trust-root,5FTPS), with zero failures/errors/skips. Its exact FileCore patch and runtime archive hashes were independently verified and are required by the final conformance gate. Earlier harness failures (duplicate Kotlin versions and missing Commons IO) are retained as failed attempts rather than pass evidence.

Self-signed/untrusted FTPS certificates are now rejected. A real server must present a certificate trusted by the platform; an owner-approved per-server CA/fingerprint enrollment flow would be separate product work, not an automatic accept-all fallback. Real FTPS providers, IPv6, proxy/NAT and session-reuse quirks remain device/provider QA. Plain FTP remains an explicit separate protocol.

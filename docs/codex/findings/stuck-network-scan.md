## Main finding and ranked causes

1. **Counted requests discarded before `doScan` begins; no production orphan recovery.** Most consistent with `Requested`, `queued`, zero files and 0/2 completed: the service flag can be false while the pending count remains 2. **M:mediaprovider/video/VideoStoreImportReceiver.java:67–70** says `if (!ProcessLifecycleOwner...isAtLeast(Lifecycle.State.STARTED)) ... return;`. The scheduler registered all members before posting delayed broadcasts; this return never calls `completeNetworkScan`. The receiver's same-URI throttle at :55–59 also silently returns without accounting. `NetworkScannerServiceVideo.startIfHandles` at :175 allows `isForeground || pendingScans > 0`, but the receiver's earlier foreground gate prevents reaching that accommodation. This is a concrete code path, not proof that the owner backgrounded the app at the critical instant.
2. **Unbounded WebDAV call or provider-lock wait occupies the single scan worker.** Supported by the missing whole-call/source deadline below; a full-process thread dump would distinguish HTTP/DNS/XML parsing from `ProviderDiscoveryGate.LOCK`. A continuously stalled socket normally hits OkHttp's inactivity timeout; a slow trickle need not. This fits zero progress, but an active service would normally display `Scanning`, and `doScan` emits `started` before root resolution/lock acquisition. It is therefore a weaker match for the exact `Requested · queued` snapshot unless later queued telemetry overwrote the started phase, the service subsequently stopped, or the snapshot is stale.
3. **Other delivery/enqueue/teardown gaps strand counted members.** `startService` throwing, an unsupported/filtered URI, `sendMessage` returning false, executor rejection, or service destruction discarding executor-queued tasks all occur before a member's `doScan` finally. There is no batch member ledger/acknowledgement/watchdog. The manifest does include webdav/webdavs (`AndroidManifest.xml:1267`), so ordinary Put.io WebDAV is not missing a filter; dav/davs aliases accepted by eligibility are not listed there. These are alternative triggers for the same accounting defect, not evidence of a specific Shield event.
4. **UI lifecycle/phase state survives real completion or never-started work.** `PreviewLibraryScan.status:257` treats `completed < sourcesTotal` as scanning even when the operation is terminal and the service is idle. Native-only queued operations lack the manual guard; out-of-order queued/terminal events overwrite the global phase. This can misdescribe idle work and coalesce later requests through the UI-owned queued latch even with both native gates clear. Losing lifecycle broadcasts can leave UI state stale independently of actual work.
5. **Scanner-alive flag left true / stale visibility.** The flag is a plain static boolean, set in service creation rather than per running task, and cleanup can throw before its clear. It is read across threads without volatile/synchronization. Less consistent with the exact `Status: Requested`: overview :283–288 chooses `Scanning` whenever it observes the flag true. Do not assume Claude's alive-flag lead is the only cause.

## Scheduler and API sync do different work

`NetworkAutoRefresh.forceRescan` broadcasts explicitly to the receiver (**M:.../NetworkAutoRefresh.java:281–285**); `medialib-next-refinement.patch:29` adds the configured-library gate. It does not force-reset either native busy gate. `onReceive` uses `goAsync` and a `NetworkAutoRefresh-bg` thread (:95–104); an atomic rescan latch wraps scheduling and clears in finally (:108–117), not after traversal. It copies indexed shortcut roots, filters eligible protocols/connectivity/inactive servers, registers a batch, and posts delayed scan broadcasts. `medialib-preview40.patch:15–30` admits internet-connected WebDAV; `medialib-preview417.patch:5–14` also treats http/https as WebDAV for this decision. No eligible roots/network unavailable terminates scheduling without a batch; manual UI then normally reaches not_started. Last-scan preference is written on successful scheduling (`medialib-preview40.patch:38`), and later service cleanup records an end timestamp if its preference extra survives. It is not a reliable proof of a completed traversal.

`PutioSyncScheduler.request:17–24` instead gates on `supernova_putio_enabled`, CASes its own `BUSY`, submits to `StreamingRepository.IO`, reads the token, and runs Put.io account/API-owned scopes (:32–39). It does not launch WebDAV traversal, manipulate scanner-alive or scan count, or emit SCAN_LIFECYCLE. Worker return/failure clears BUSY in finally; submission failure outside the lambda would not. Cancellation is checked between API work (:43–52). Its independent diagnostics use `putio_sync_*`; successful API work cannot repair orphaned WebDAV membership. Because it is invoked before the network UI busy check, a coalesced manual network request can still request API sync.

## Why queued can outlive the 15-second guard

`PreviewLibraryScan.requestNetwork:153–178` creates a manual operation, queues native scheduling, and installs exactly one timer capturing that operation ID. It only terminates if **both** ID still matches and phase is exactly queued. It finishes the UI operation, not the native batch or service.

The lifecycle receiver at :66–73 can instead create an operation for native telemetry: `operation.isEmpty()` or `operationEnded && (next.equals("queued") || next.equals("started"))`. There is **no timer in that path**. Thus a direct native automatic scan can remain queued indefinitely. Also a delayed native queued event after the manual timer's not_started/finish creates a new operation with no guard. A new batch that changes operation ID invalidates the old captured timer. For a normal two-source manual request, queued events before 15 seconds with the same operation ID do **not** by themselves bypass the guard: it should show not_started, but the orphan native count still blocks requests. Distinguish these cases instead of claiming every queued broadcast cancels the guard.

All accepted events unconditionally assign `phase = next` (:79); there is no monotonic transition check. Scheduler background thread emits queued after posting main-thread delivery, so delayed/order interleavings can overwrite started with queued. `status:257–269` prioritizes alive or unfinished totals over not_started/terminal states. `overview:283–295` calls only the alive flag “Scanning”, phase queued “Requested”; it can contradict `active()` and `status()`. `PreviewScanProgress:9–15` records terminal sources but allows later phases to replace displayed counters, and accepts a different batch as fresh without ordering validation.

## Can webdav.put.io/TV listing block forever?

The indexer uses **synchronous raw listing**, not the UI `WebdavListingEngine` timer: **M:NetworkScannerServiceVideo:694** resolves root through MetaFileFactory; :775 invokes FileVisitor; **M:FileVisitor.java:77** calls `file.getRawListerInstance().getFileList()` on the owning scan worker. **F:filecorelibrary/webdav/WebdavFile2.java:213–221** performs depth-zero PROPFIND before traversal. **F:.../WebdavRawLister.java:39–54** performs depth-one PROPFIND and materializes the complete result. One serial executor handles all roots (**M:NetworkScannerServiceVideo:137,401**), recursion depth is limited to 15, but source elapsed time and directory count are not bounded.

**F:.../WebdavUtils.java:61,111,191–195** constructs OkHttp clients without explicit connect/read/write/call timeouts. These retain OkHttp defaults (10-second connect/read/write inactivity limits, no whole-call timeout), not an explicit zero read timeout. `listResources`'s only application retry is a single selective-property fallback to allprop on HTTP 400/405/501 (`filecore-preview414.patch:869–879`); no infinite application retry loop was found. Authentication stops once Authorization was already attempted (**F:WebdavUtils:159–160**); OkHttp also owns finite redirect/recovery behavior. Redirect probing now uses OPTIONS and verifies a DAV endpoint (`filecorelibrary-supernova146-upstream.patch:3796–3840`), with the same missing whole-call deadline.

Therefore an entirely silent ordinary connected read should fail on inactivity, but a server that trickles bytes below that timeout, a pathological parse, DNS/platform stalls, a large/deep listing, or indefinite monitor wait is not bounded by an end-to-end source deadline. No claim is made that Put.io actually sent such a response. `ProviderDiscoveryGate.LOCK` wraps performScan (`medialib-preview417.patch:109`), and local import uses the same gate; JVM monitor acquisition is not made bounded by interrupt. FileVisitor's interrupt checks (`medialib-supernova144-reconciliation.patch:19`) only run between calls. WebdavListingEngine.abort merely sets an abort flag (**F:WebdavListingEngine:70–72**); its UI listing timeout is not the scanner's cancellation mechanism. A local import finishing every 15 minutes neither releases an orphan network count nor proves any WebDAV worker is active.

## Library Health: summary counts markers, categories join visible records

`LibraryHealth.report:34–50` counts **every** `media:` preference key: `missing.add(String.valueOf(entry.getValue()))`, then `missing.size()`. `LibraryHealthActivity.update:134–146` only lists entries from `snapshot.technical` and tests the entry's current ID through `LibraryHealth.state:24` (`health.contains("media:" + video.getId())`). Source Problems only enumerates offline:/problem: keys (:148–150), not media: keys. Thus two stale/excluded/unmapped markers can yield “Confirmed missing: 2” and all empty categories. `choose:196–209` derives “healthy” exclusively from these groups and sourceIssues, yet prints the independent raw report alongside them.

The snapshot deliberately excludes out-of-policy URIs (`PreviewLibraryLoader:586–587`), may skip malformed records (:618–621), and is not the same population as preferences. A further concrete stale-marker path: reconciliation first writes availability missing (`medialib-supernova144-reconciliation.patch:77–85`), then allows complete WebDAV traversal to retain `needsDelete`, and bulk deletes those absent indexed rows. `SupernovaLibraryPolicy.availability` stores media:id; returning files clear by ID (`medialib-supernova135.patch:292,376–381`). Neither `sourceAvailable` (:383–387) nor this deletion path removes the associated media: marker. Removed rows cannot appear in technical, so their markers can remain counted indefinitely. The code contradicts the policy's general “retained records” explanation here. Without the actual two keys and corresponding database rows, stale deletion versus exclusion cannot be distinguished; no pagination cap is assumed.

A proposed health correction is to use one ID/visibility-aware issue inventory for summary and categories, show excluded/orphan markers explicitly when meaningful, and reconcile markers transactionally when rows are actually removed. Do not silently delete library records or markers solely to make the counts match.

## Proposed fix for candidate 1 (words only; not applied)

Give every counted member a batch-and-source identity and explicit queued/running/terminal ownership. Make the scheduler-to-receiver-to-service-to-executor handoff acknowledged. For registered work, either permit the pending batch through the receiver's background gate using the appropriate Android service scheduling mechanism, or record an explicit not_started failure and complete that exact member. Apply the same compensation to throttling, unsupported intents, service-start failures, message/executor rejection and teardown of never-started tasks. Release each member exactly once; don't clear a shared counter on a timer while a worker can still mutate the library.

Add a bounded start acknowledgement deadline, a cancellable source deadline with owned HTTP-call cancellation, and recovery that fences old batch generations before replacing them. Reconcile actual ownership on resume. UI and native scheduler should consume the same batch state; every operation, including native-only ones, must reach a terminal state or a visible retryable failure. Preserve offline/partial-listing record protection. Don't solve this by simply bypassing `active()` or unconditionally calling resetNetworkScanCount, which would allow overlapping writes.

**Test that proves the top fix:** with two indexed WebDAV roots and controlled main looper/process lifecycle, register a native batch while STARTED, move to STOPPED before the 100/2100-ms dispatches, drain both callbacks, and return to STARTED. Assert either both members were serviced once or each rejected member received exactly one not_started terminal result; count reaches zero, alive matches real service ownership, no source is left queued, and a manual retry starts a new batch. Repeat with a receiver duplicate inside 500 ms, startService failure, rejected executor, service destruction with one running/one queued task, native-only queued events, and late old-batch completion. Assert no double-decrement or late database mutation, one terminal batch event and no false metadata-success handoff. Add MockWebServer silent/trickle/disconnect tests for the proposed source deadline, plus a health test with an excluded ID and a deleted-row marker. These are proposed tests; none was executed in this read-only run.

For device confirmation, collect existing diagnostic lifecycle IDs, receiver/background/throttle logs, observed count/alive, and a thread dump at the same instant. A queued-only batch with no service/worker and positive count supports #1; a live scan worker in PROPFIND/monitor wait supports #2. Avoid logging credentials or full authenticated URLs.

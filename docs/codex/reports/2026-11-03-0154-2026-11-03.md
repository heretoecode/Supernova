### Why stage 3 cannot be deleted safely in the specified order

The proposed stage 3 class set is not independent of the stage 4 phone shell:

- `browser/BrowserActivity.java:43,183` imports and instantiates `BrowserListOfSeasons` in its cover-launch receiver.
- `browser/MainActivity.java:90,91,490,491` uses both `BrowserListOfSeasons` and `CursorBrowserByVideo`.
- `browser/BrowserCategoryVideo.java:36–47,71–73,327–363` imports and routes to the proposed library-screen deletions (movies, shows, playlists, recently played/added and others).
- `browser/QueryBrowserActivityVideo.java:25,33,55–57` imports, stores and instantiates `BrowserByQuery`; this Activity still has exported search contracts in the manifest. Deleting that fragment without migrating the search host is not safe.
- `browser/adapters/GroupOfMovieAdapter.java:31,82–84,161` still needs `BrowserMoviesBy` constants and `getMultiposterThumbnailRequest`; this is a remaining phone-client dependency, unlike the neutral retained-TV loader dependency separated in stage 1.
- `cover/TvShowCover.java:22,210` still names `BrowserListOfSeasons` for its launch contract.
- `res/layout/browser_item_header_show.xml:88,110` inflates `ArchosFadeView`; the retained phone show-header screen still uses this layout. Merely deleting the class leaves a runtime inflation failure.

Removing those callers as part of stage 3 would perform stage 4's shell/browser
removal early. Leaving them unchanged while deleting stage 3's library classes
would leave uncompilable Java references. I did neither; no placeholder classes,
empty handlers or disabled assertions were introduced to conceal the dependency.
A revised prerequisite extraction/routing stage, or an approved regrouping of
these dependent phone shell/library removals, is needed before proceeding.

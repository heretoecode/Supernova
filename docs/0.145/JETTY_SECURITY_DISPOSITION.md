# Jetty 9.2.30 advisories — 0.145 review and mitigation

The nine OSV findings remain valid **dependency-version findings**. No advisory is suppressed and the bundled Jetty version has not been relabelled as fixed. Reviewed code: MediaLib's `NovaJettyServletContainer`, `NovaUpnpService`, jUPnP 3.0.5 servlet/client sources, and the exact Jetty 9.2.30 server/client sources from Maven Central.

## Implemented changes and evidence

`.github/build/medialib-supernova145-jetty-security.patch` is applied by all 0.145 workflows. It changes only the UPnP transport boundary and introduces no dependency, SDK-floor, schema, TLS-trust, application-identity or UI changes. HTTP close-after-response is protocol-correct and already used by jUPnP's outgoing client; it trades connection reuse for unambiguous exchange lifetime.

`Jetty145SecurityTest` has **11 actual-library integration cases** covering normal GET/POST/NOTIFY/SUBSCRIBE/UNSUBSCRIBE bodies, async NOTIFY, chunked bodies, signed/duplicate/overflowing lengths, TE/CL conflict, pipelining, opaque servlet/parser errors, preserved SOAP faults and outbound malformed/normal/IPv6 endpoints. Local Java 17-target compilation and JUnit execution against the exact pinned Maven jars pass. An unmodified old-container negative control fails five of the original nine server cases, including real secret-path disclosure and accepting `+4` content length. Focused Android CI 40762572889 on `d6e106ffa27fce88cbfb4ebbfe305954c7e73f60` passed all 23 new maintenance cases (including these 11), with independently downloaded XML/digest verification and lint zero errors/1,795 warnings. Final protected Android/native/signing run 40762577939 also passed all 1,158 cases, including these 11, before signing the exact tested payload.

## Genuinely deferred library work

A supported Jetty/jUPnP transport migration or maintained security backport is still needed to remove all nine package-level findings. The upstream itself retains 9.2.30 for the API-23 floor; newer Jetty is not a verified drop-in Android replacement, and a one-class parser override would create duplicate-class, ABI and provenance risks. A safe upgrade requires API-23/device coverage, custom UPnP method/async/IPv6/provider regressions, runtime hashes, SBOM/legal review and APK validation. Raising the minimum SDK, dropping UPnP, disabling HTTPS providers, or weakening certificate checks is not used as a shortcut. Real provider/device compatibility and residual legacy-library risk remain explicit QA limitations.

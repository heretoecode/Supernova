# Settings coverage, defaults and restoration

**No, every modified setting is not preserved.** This conclusion follows directly from saved active keys rejected by `BackupPrivacy.setting`, independently of runtime testing. XML alone is insufficient: dynamic settings, player controls, source scheduling and named stores are mapped below.

## Common storage and intent contract

Default prefs use Android's package-default SharedPreferences (`<package>_preferences`, under `shared_prefs`). Portable JSON is an exact typed map of **stored allowlisted values after sanitization and selected history removal**. It does not inspect defined defaults or provenance. [SettingsBackup.java:13](https://github.com/heretoecode/Supernova/blob/b3504c2c4b1725f3070416d14b63e53ae1db3d74/src/main/java/com/archos/mediacenter/video/utils/SettingsBackup.java#L13), [BackupPrivacy.java:231](https://github.com/heretoecode/Supernova/blob/b3504c2c4b1725f3070416d14b63e53ae1db3d74/src/main/java/com/archos/mediacenter/video/utils/BackupPrivacy.java#L231), [BackupPrivacy.java:290](https://github.com/heretoecode/Supernova/blob/b3504c2c4b1725f3070416d14b63e53ae1db3d74/src/main/java/com/archos/mediacenter/video/utils/BackupPrivacy.java#L290).

| State of a key | Current export | Current restore |
|---|---|---|
| Changed, stored, allowlisted | Included with stored type/value, sanitization may change a URI/string | Restored value; receiving consumer can migrate/clamp/reinterpret it |
| Unchanged default already persisted by initialization/inflation | Also included | Pins that stored value even if next version changes default |
| Explicitly changed back to default and persisted | Included identically to any other stored value | Preserves value, but cannot distinguish explicit intent from incidental initialization |
| Never stored or explicitly removed | Absent | Default prefs are cleared; receiving consumer supplies its own default |
| Stored but unallowlisted, secret, UI-forced or selected-history excluded | Absent regardless of whether user changed it | Lost from default prefs when restore clears the store; not retained from destination |
| Dynamic family member | Same rule using prefix/regex, not a finite key enumeration | Restored key as written; no referential ID remapping |
| Named group present | Only accepted group-specific keys, same typed representation | Clear/replace that entire named group |
| Named group omitted | Not represented | Live group remains; this differs from default prefs and missing DB entries |
| Type/default changes between versions | No per-key schema/default version saved | Getter type mismatch or altered semantics needs future versioned migration; manifest's app version is not such a migration |

Thus the requirements **unchanged defaults omitted** and **explicit reset intent preserved across default changes** are not both satisfied. Never infer “unchanged” from `value == old default`: explicit selection of that value can be intentional. Proposed schema should record `explicit value`, `follow current default` and key schema/default origin separately, with legacy stored values conservatively treated as explicit unless initialization provenance is proven. Do not silently convert historic users to new defaults.

## Future settings policy (proposed)

Define a versioned registry of portable user choices with store, typed key, default, provenance/intent, migration and category. Separate device-local/auth/transient/cache keys. Preserve named and default category omission with an explicit merge/replace policy, never global `clear()` for a partial category. Save user default-reset intent instead of calculating it from values. Validate original/staged settings without creating or committing live preference data. Include currently missing genuine settings after owner approval; keep OS grants, secrets and trust excluded. Do not make plaintext credentials a “complete backup” solution.

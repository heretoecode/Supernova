## Can matching and paths be selected separately?

**Not safely in the current snapshot architecture.** Deleting `_data`/source fields would remove the bridge from file to scraper identity and affect URI uniqueness, scanners, local membership and playback. Paths alone disclose filenames/source topology but do not preserve manual identification. Provider title IDs alone identify a title but do not associate it with a physical file. A “match without paths” switch promising equivalent restoration would be deceptive.

Proposed optional **Media identification matches** bundle contains a schema-versioned source identity + locator (path/URI as necessary), provider kind/ID, episode coordinates, sufficient local-reference remapping and manual match selection. Switch Off must exclude locators from **every other entry**: settings roots/exclusions, shortcuts, provider links, named health/source state and embedded metadata paths can also leak them. Sources/bookmarks remain separately selected and may deliberately include paths under their own warning; turning matching off is not a claim of a path-free archive when those switches are on.

Logical history/collection/row member identities can independently reference TMDB entities without storing physical paths. Unmatched media currently has exact-location fingerprints; a privacy-preserving portable identity/future optional content fingerprint is a separate design choice, not implemented. HMAC/device-specific salts would trade portability; plain hashes are pseudonymous and can be dictionary-tested against known locators. If matching is off, unresolved unmatched members must be retained transparently or require explicit dependency selection, never silently drop them.

## File-path/privacy analysis

`BackupPrivacy.cleanText` parses URI-shaped text, strips query and fragment, removes authority user-info when host is available, and keeps host/port/path. Raw absolute paths, labels, account IDs, names and arbitrary non-URI text remain. `secretKey` blocks/nulls password/token/credential-like column/key names, but username/account-like DB fields and secrets embedded in plain names are not generically removed. JSON cleaning removes secret-named keys; it is not a full semantic secret scanner. Privacy validator repeats these structural rules; it does not establish absence of every possible secret. Library rows can reveal server/share names, folder structures, filenames, titles, volumes and watch choices. Source credentials DB is excluded, but source identity/path is **not** a credential-free anonymity guarantee. Public evidence uses only developer-owned key/schema names; no personal locations or user records.

For unmatched history, `ViewingHistory.identity` instead keeps nonsecret media-selecting query pairs, then SHA-256 hashes the normalized URI. The backup sanitizer drops **all** URI queries from exported physical rows. **Inferred compatibility risk:** query-selected items can lose distinctions or fail to reproduce their original `file:<hash>` identity after restore. No real archive has been tested for this case. Do not “fix” by restoring authenticated/signed queries; define a separate safe locator scheme. ## History and resume selection

All four keys default On: Track History / Save Resume control future recording; Include History / Include Positions control export filtering. Private mode prevents new history recording; it does not erase previously recorded data or make an existing backup anonymous. History `duration` remains when rows retained; it is not zeroed when history off. `Archos_bookmark` is controlled by resume only; per-file player params/subtitle delay/ratio and source/list/row state are not cleared by these toggles. `selectedSettings` reads resume but does not use it to filter any settings; only the history switch removes those named prefixes. Continue Watching reconciles identity history with locally available episodes/files and saved display/dismissal rules. Unavailable sources, cleared legacy flags, failed playback start, completion and per-file bookmarks affect eligibility. A restored positive position does not by itself certify the row will appear. Reuse maintenance report 07 and the approved 0.139 Continue Watching/playback investigation; this audit does not change that scope.

## User data versus caches

Durable: manual selected matches, collection/list definitions and membership, Home/custom page configuration, hidden/pinned/preferred-version state, sources/bookmarks, watched history, resume and per-file playback customisation. Provider metadata, derived technical scan data, discovered server status, image files and enrichment queues are generally regenerable, but provider outages/removals or unmatched media can prevent perfect reconstruction. No independent general “user tags” table was found in the known schema: genres are provider metadata, custom row genres are filter rules, collections are user membership. Do not market an unsupported tags-backup category. Recommend a future durable metadata-override ledger before excluding all metadata from new logical exports.

Already-decided no-artwork exports may lose personal/custom image choices; this is explicitly acknowledged for owner compatibility policy, with no artwork toggle proposed. Current regeneration uses retained provider IDs/URLs, and missing episode stills get a targeted provider lookup without rewriting watched/resume state.
